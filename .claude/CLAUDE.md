The shared conventions imported above apply to all repos. This file contains repo-specific instructions: anything here overrides the Defaults section of CLAUDE-COMMON.md; its Invariants always apply.

## Yantra Specifics

- **Stack**: Flask backend + Vue.js frontend (see [SMTW-WebApp-Base.md](SMTW-WebApp-Base.md)); MariaDB (PyMySQL + DBUtils pool); Keycloak realm `Office.smtw.in`. Product plan: `docs/Plan.MD`. Database schema: `docs/schema.md` (tables, built and planned) and `docs/schema.html` (relationship diagram, generated from a migrated database) — update both when a migration adds or changes a table or column. Domain knowledge: `docs/Maintenance-Philosophy.md` (rules, TPM-based) and `docs/Plant-Facts.md` (the factories as they are) — read both before designing any maintenance module.
- **Standards and best practice**: Yantra must help the plant adopt industry maintenance standards and best practices (TPM, ISO 14224, EN 13306, ISO 55000, SMRP KPIs). At every design step, name the relevant standard or practice, explain in plain terms what it says and why, show how the proposal follows it — or state where and why it deliberately departs — and prefer standard terms over inventing local ones. The project owner is learning maintenance practice as the project goes.
- **Step workflow**: work is done in numbered steps (`S001`, …) whose brief, reviews and implementation report live in `docs/steps/` — read `docs/steps/README.md` for the file naming, finding IDs and gates before planning, reviewing or coding a step. Never code a step whose brief is not `Approved` by the user. `/step` (skill) orchestrates the cycle from one terminal with the `brief-reviewer`, `coder` and `code-reviewer` subagents (`.claude/agents/`). `/step ls` builds its table from one run of `tooling/step-ls.bat`, and `/step check` (consistency of the step files, read-only) starts from `tooling/step-check.bat`, and `/step stats` (rounds, findings, time, tokens, e2e cost) from `tooling/step-stats.bat`; the planner checks a draft brief's references with `tooling/step-brief-facts.bat S0NN` before review; at gate B each step is snapshotted as a commit under `refs/steps/S0NN` (`tooling/step-snapshot.bat snapshot|list|adopt`, step skill § Snapshots), so steps get their own commits while the next one is coded (`tooling/steps/`: `step_facts.py` reads the step files and git once; the scripts judge nothing the planner should).
- **RBAC deviation (S011)**: roles do not all come from the token. Keycloak gives only `maintenance_team` (may log in, grants nothing), `it_admin` and admin (`mspv-apps-admin`). The maintenance roles (`config_rbac.SITE_ROLES`) are held in Yantra per person and site (`memberships`, `person_units`; Team in Masters) and are read lazily per request. Keys in `config_rbac.SITE_SCOPED` are checked at the record's site (`has_perm_at`, `accessible_unit_ids(cur, key)`); others use the union. `config_rbac.py` stays the single source of roles and keys; fail-closed and the admin bypass are unchanged. New site-scoped keys must be added to `SITE_SCOPED`. Keycloak setup: `docs/Keycloak.md`.
- **Ports (dev)**: backend 5001, Vite 5176, MariaDB 3307 (3306 is SaralWeb's dev DB). Container backend listens on 5000.
- **Dev commands** (also PyCharm run configs):
  - DB: `tooling/dev/dev-db-up.bat` / `dev-db-down.bat` / `dev-db-reset.bat` — compose project `yantra-dev`, DB `vel_yantra_master`; the tests make their own (below)
  - Backend: PyCharm "Backend" (`FLASK_DEBUG=1`, `DEV_AUTH_BYPASS=1`, interpreter `uv (Yantra-backend)`); frontend: "Frontend" (`npm run dev`)
  - Tests: `tooling/run-tests.bat` (all four suites: backend, frontend, deps, tooling; every suite runs, then one summary line each), `run-backend-tests.bat` (needs the dev DB; pytest arguments pass through, e.g. a test file), `run-frontend-tests.bat` (vitest arguments pass through). Output is quiet (`-q`, failures in full); each suite's whole output goes to `scratch/<suite>-tests.log`, and its last line says PASSED/FAILED, the counts, the time and the log path — read that line and the log, do not re-run to see the summary.
  - Backend tests in parallel (pytest-xdist, `--dist loadscope`, `YANTRA_TEST_WORKERS` default 8; the full suite takes about 40 s, 6 min before): each worker has its own databases `vel_yantra_test_<run>_<worker>` and `vel_yantra_upgrade_<run>_<worker>` (`backend/tests/db_names.py`), created by the tests and kept between runs; `<run>` is `YANTRA_TEST_RUN` (default `dev`). Two runs at the same time need different `YANTRA_TEST_RUN` values. `-n 0` runs one process (saves about 4 s on one small file). Named locks (`GET_LOCK`) are server-wide, so their names carry the database's (`local_db.named_lock`). Old test databases are never dropped by the tooling (about 11 per run name): drop them by hand now and then, a dev chore for a free moment, never during a test run (the next run rebuilds what it needs, about 1 min). Two steps, in a terminal in the repo root: (1) write the list, which names the unused `vel_yantra_test` and `vel_yantra_upgrade` of before the parallel runs and every `vel_yantra_test_*` / `vel_yantra_upgrade_*`, and read it: `docker compose -f tooling/dev/docker-compose.dev.yml exec -T mariadb mariadb -uroot -pdev-root-password -N -e "SELECT CONCAT('DROP DATABASE ', schema_name, ';') FROM information_schema.schemata WHERE schema_name IN ('vel_yantra_test','vel_yantra_upgrade') OR schema_name LIKE 'vel\_yantra\_test\_%' OR schema_name LIKE 'vel\_yantra\_upgrade\_%'" > scratch/drop-test-dbs.sql`; (2) run it: `docker compose -f tooling/dev/docker-compose.dev.yml exec -T mariadb mariadb -uroot -pdev-root-password < scratch/drop-test-dbs.sql`. (`dev-db-reset.bat` drops everything, including `vel_yantra_master`.)
- **Secrets**: `backend/secrets_app.py`; in prod rendered by Ansible (`smtw_erp_devops/erp_server/yantra/secrets_app.py.j2`) — keep `example_secrets_app.py` field names in step with that template. Missing file falls back to the example only in dev/test.
- **Files (S006)**: uploads live under `DATA_DIR` (default `<repo>/data/`, gitignored); in prod `DATA_DIR=/app/data`, the App-FS NFS share bind-mounted by the devops compose. Served only through permission-checked routes, never as static files.
- **DB may not exist**: the app must start and serve while the DB is unreachable or not created (fresh deploy). `local_db.ensure_schema()` retries migrations every 30 s; `get_db()` raises `DBUnavailable` → 503.
- **Migrations (S025)**: v1–v13 were squashed into one migration **v20** (21-10-2026); new migrations start at **v21**. A migration that cannot run on existing data gets a precondition in `local_db._PRECONDITIONS` (checked for every pending version before any is applied; a refusal changes nothing and shows in Settings › Database), never an edit of an applied migration. The old texts live only in `backend/tests/fixtures/migrations_v13.py` (frozen).
- **Release**: Release (patch/minor/major) run configs → `tooling/common/release.py`, with `TEST_CMD` / `BUILD_SCRIPT` / `DEPLOY_SCRIPT` and the deploy settings set as run-config env vars (a hook blocks writing `release.env`). `TEST_CMD` is `tooling\release-tests.bat`: the four unit suites, then the browser tests at the Full level (S047; also when the unit suites were red; needs Docker Desktop for the iPhone; report and lane logs copied to `scratch/release-tests/e2e/`; exit 0 only when both are green; Vite in the worktree serves the junction's files by their real path, so `vite.config.js` adds the real `node_modules` to `server.fs.allow`), on a temporary git worktree of HEAD (`%TEMP%\yantra-release-tests`, `frontend/node_modules` linked by a junction) with `YANTRA_TEST_RUN=release`, logs in `scratch/release-tests/`, so edits and test runs in the working folder during a release cannot touch it. **Never remove that worktree by hand** (`git worktree remove`, the IDE): it is locked because `frontend/node_modules` in it is a junction to the working folder's, which git would empty; run `tooling\release-tests.bat` again, which removes the junction first. `tooling/build/build.bat` builds the images from a temporary worktree of tag `v%VERSION%` (`%TEMP%\yantra-build-v<version>`), never from the working folder; `--dry-run` runs the git refusals (dirty tree, no tag, HEAD not at the tag) and the checkout only (no registry check, login, build or push).
- **Deploy**: `tooling/deploy.py` over plink to PuTTY session `ansible-ws` (`/home/kla/smtw/erp_server`): stamps `YANTRA_VER` (bare version, e.g. `"0.1.2"`) in `yantra/vars/settings_vel_yantra_master.yaml` (relative to `erp_server/`), then runs `./erp_spanner.py deploy vel yantra master`. The compose pins the tag, so a VelKilnMaster-style `compose pull` would not update. `erp_spanner.py` exits 0 even when the playbook fails, so `deploy.py` checks the PLAY RECAP itself. Then (S025) it polls `DEPLOY_HEALTH_URL` (the public `/api/health`, set in the Deploy and Release run configs) until `schema_ready` is true, for up to 3 minutes; on any failure after the stamp it prints the rollback lines (stamp the previous version, redeploy; restore db-server's dump first if the new schema applied). `--check` is read-only; `--stamp-only` skips the Ansible run. "Deploy" run config = redeploy current `VERSION`. `tooling/build/build.bat` refuses a dirty tree, a HEAD that is not the commit tagged `v%VERSION%`, and a version already in the registry.
- **npm**: npm 10.9 crashes (`edgesOut`) resolving vitest's optional peers — use `npx npm@11 install` to change dependencies; `npm ci` (Docker) is fine.
- **Network gate (S013)**: `config_rbac.INTERNAL_ONLY_ROLES` is a **deny list** (roles refused from outside the internal ranges in Settings › Network), a deliberate departure from the base's `access:wan` allow list; today only `it_admin`. Admin bypasses. Client IP from `X-Real-IP` only.
- **Worker (S013)**: `worker.py` drains `task_queue` (one worker, `named_lock(LOCK_WORKER, database)`), and enqueues the daily tasks of `scheduled_tasks.SCHEDULE` (IST) itself — no APScheduler.
- **Software inventory (S022)**: `sbom/*.cdx.json` (CycloneDX 1.5, one per lockfile, named after its folder) are generated from every tracked `uv.lock` / `package-lock.json` and committed; never edit them by hand, and **commit `sbom/` with every dependency change**. Run the check with `tooling/run-deps-audit.bat` (any OS: `uv run tooling/deps/audit.py`): it regenerates `sbom/`, looks every library up in OSV, flags direct dependencies with no release in 12 months, and writes `scratch/dependency-report.md`. Exit codes: **0** clean, **1** a critical, high or unknown-severity vulnerability, **2** the check could not be completed. It is not in `run-tests.bat` (only its unit tests are: `run-deps-tests.bat`). `tooling/deps/` names no project and is meant to move to `smtw-common`.
- **Browser tests (S024)**: Playwright specs in `frontend/e2e/`, run by `tooling/run-e2e-tests.bat` (needs the dev DB container; creates `vel_yantra_e2e` and installs Chromium itself; WebKit runs in Docker, below). Its own stack: backend `127.0.0.1:5002` (`tooling/e2e/e2e_backend.py`: `vel_yantra_e2e` dropped and rebuilt every run, `DATA_DIR` `scratch/e2e-data/`, identity from the `X-Test-Role` / `X-Test-User` headers, a header-less request gets no access), Vite 5177, seed `tooling/e2e/seed_e2e.py`; three projects (Pixel 7 Chromium, iPhone 14 WebKit, desktop Chromium); report in `scratch/e2e-report/`. **WebKit in Docker (S046)**: on Windows, WebKit multiplies the emulated pixel ratio by the display scale (125 % gives a 312 px iPhone window), so `phone-webkit` runs in a container instead. When a run includes `phone-webkit`, `run_lanes.py` (inside the e2e lock) starts `mcr.microsoft.com/playwright:v<version>-noble` (the version of `frontend/node_modules/@playwright/test`) running `playwright run-server`, published on `127.0.0.1:3999` only (container `yantra-e2e-webkit`, log `scratch/e2e-lanes/webkit.log`, npm cache in the volume `yantra-e2e-npm`), sets `E2E_WEBKIT_WS`, and `playwright.config.js` connects `phone-webkit` to it with `exposeNetwork: "<loopback>"` (the stacks stay on the host); the container is removed after the run. The first run of a Playwright version pulls the image (about 2.5 GB). A run that names projects without `phone-webkit` starts no container. `E2E_WEBKIT=native` runs WebKit on Windows (S045's guard in `e2e/support/test.js` then skips it on a scaled display). If the server cannot start, the run stops before any lane with a message naming the cause. **Levels (S047)**: `run-e2e-tests.bat --level=basic|normal|full` (no flag is Normal). **Basic**: the `@smoke` tests (`journeys.spec.js`, four journeys of real work end to end, and `screens.spec.js`) on `phone-chromium`. **Normal**: every test on `phone-chromium` (the shop floor's Android phone carries the logic tests), and on `desktop-chromium` only the `@device` tests (`E2E_LEVEL=normal`, a project `grep` in `playwright.config.js`). **Full**: every test on all three projects. A `--project` the caller names wins over the level's devices, with no `@device` filter; Basic refuses a `--grep`. **Tags**: `@device` marks a test whose *purpose* is a layout check (title names fits, in view, on screen, scrolls to, no sideways scroll, above or below; or its main assertion is a geometry), or that runs only on, or asserts differently on, a project other than `phone-chromium`, or is in `screens.spec.js`; a geometry helper inside a flow test (`expectDialogFits`, `expectFieldMessage`, …) and a skip of `phone-webkit` alone do not tag it (Full checks those per device). A new test is untagged unless the rule applies. **Lanes**: the run is split into `E2E_LANES` parallel lanes (default 6, `tooling/e2e/run_lanes.py`), each on its own stack — database `vel_yantra_lane<n>_e2e`, backend `5010+n`, Vite `5180+n`, files `scratch/e2e-data/lane<n>/`, log `scratch/e2e-lanes/lane<n>.log`, Vite dependency cache `scratch/e2e-vite-lane<n>/` (`E2E_VITE_CACHE_DIR` → `vite.config.js` `cacheDir`, S047: six servers optimising into one `node_modules/.vite` race on its rename) — and the blob reports are merged into the one HTML report (and `scratch/e2e-report/results.json`); `E2E_LANES=1` runs the single stack above. The lanes are **planned** (S047): one `playwright test --list` run gives the tests per group (a spec file in one project), each group is weighed by its measured seconds per test (`scratch/e2e-timings.json`, updated after each run), and the groups are packed longest first into the least loaded lane; each lane gets its groups in `E2E_LANE_PLAN`. A test named by line (`x.spec.js:42`) falls back to `--shard`. A run that selects no test stops with exit 1. **Who runs what**: the coder makes targeted runs (Normal with spec files: the changed screens plus `screens.spec.js`) as often as it needs, may run Basic for a quick whole-app check, and runs the whole suite at Normal once when the step's coding is done (again only with a reason it states); fix rounds make targeted runs only; the code reviewer never runs the whole suite and re-runs only what a finding of its own needs; the Full level runs in the release and when KLA asks; also from `/smtw-review`. One run at a time per machine: `scratch/e2e-run.lock` and the timings live in the **main working folder's** `scratch/` (the parent of `git rev-parse --git-common-dir`), so a run from the release's worktree and one from the working folder wait for each other; **never** in `run-tests.bat`; at the Full level in the release. Checks a browser cannot judge are rows of `docs/steps/device-checks.md`.
- **Notifications (S021)**: Yantra is a PWA (`frontend/public/manifest.webmanifest`, `sw.js`). The service worker only shows a pushed alert and opens its ticket: it **caches nothing and has no `fetch` handler** (online-only; the stale-bundle check is unchanged) — never add caching to it. Alerts are enqueued in the ticket's transaction (`alerts.py`; rules in the pure `alerts_core.py`, the same for every channel) as `ticket_alert` / `ticket_escalate` tasks; the worker fans out one `push_send` per device (`push_subscriptions`, v24). A send task records its failure on its own row and commits before raising `NoRetry` / `RetryLater` (`task_handlers.py`). Push addresses are allowed only at the known push services (`push_core.ALLOWED_PUSH_HOSTS`, SSRF guard). VAPID keys are secrets in `secrets_app.py` (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`; empty = push off), made by `tooling/dev/make_vapid_keys.py`; production's pair is never rotated casually (it ends every subscription). `pywebpush` is called only in `push_sender.py`. **Email (S032)** is the second channel: each alert kind names its channels (`alerts_core.CHANNELS`; today only *Ticket closed* → email, to the site's managers); `smtplib` is called only in `mail_sender.py` (Mailgun, STARTTLS); secrets `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` (email is off unless host, port and from are set). **Policy: SMTP hosts, ports and email addresses never go into the repo** (no code default, example, test value or doc) — they come only from the Ansible vars; tests use reserved values (`example.test`); a person's address is the Keycloak token's `email`, copied to `people.email` by `/api/auth/me`, never typed, shown only to IT admin and its owner; `email_send` payloads carry the person id, never the address.

## Docs to keep current

## SMTW-Review

Read by `/smtw-review`: this repo's own points for the audit.

- **Browser tests**: the audit may run `tooling/run-e2e-tests.bat` (Playwright; `phone-webkit` needs Docker Desktop running and the WebKit image, S046, or `E2E_WEBKIT=native`) when it helps: to confirm a finding about a screen, a permission shown or hidden, or a flow (Normal with the spec file), or at `--level=full` to report the suite's state on every device. Run it in the background (a full run can pass the Bash tool's 10-minute limit; it needs the dev DB container up). Not required on every audit. Report the result, and every failing test with the screen it opens and the step it checks (the test names start with the step, e.g. `S017: …`; the spec files map to steps: `tickets-raise` S017/S018 A1, `tickets-work` S018/S052, `tickets-notes` S027, `notifications` S021, `me` S031, `masters` S016/S037/S038/S043, `equipment` S003/S006/S012/S038/S043/S039/S044, `readings` S039/S040/S050/S051, `asset-list` S015, `labels` S014, `journeys` S047, `screens` every route). Tests marked as expected to fail or skipped carry a comment naming the open fault.
- **Steps**: check each committed step's status against its impl report (checks `[auto]`, ticked, skipped or pending) and list the steps that are committed but not `Done`.
- **Device checks**: list the open rows of `docs/steps/device-checks.md`.
- **Previous audit**: read the latest `docs/review/*-smtw-review.md` and report the status of each of its findings.
- **Migrations**: `_MIGRATIONS` starts at v20 (squashed 21-10-2026); v1–v13 live only in `backend/tests/fixtures/migrations_v13.py` and are never edited; a migration that touches rows that exist in production carries a `_PRECONDITIONS` entry and a test from the production schema. Check both on every migration after v20.
- **Meter readings (S039)**: every counter reading path (today `meters.log_reading`, which the S040 sheet also uses, row by row; later PM and IIoT feeds) takes the node lock first (`load_node_for_user`, `for_update`) and checks both neighbours (`meters_core.counter_error`, against the nearest active readings before and after the time taken). A path that skips the lock lets two writers pass the order check together; a path that checks only the latest reading lets a back-dated typo through.
- **How this section grows**: a step that adds something a later audit should check (a new invariant, a check that only a full run shows) adds a point here; the planner proposes the point in the step's brief.
