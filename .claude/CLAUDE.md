## Yantra Specifics

- **Stack**: Flask backend + Vue.js frontend (see [SMTW-WebApp-Base.md](SMTW-WebApp-Base.md)); MariaDB (PyMySQL + DBUtils pool); Keycloak realm `Office.smtw.in`. Product plan: `docs/Plan.MD`. Database schema: `docs/schema.md` (tables, built and planned) and `docs/schema.html` (relationship diagram, generated from a migrated database) — update both when a migration adds or changes a table or column. Domain knowledge: `docs/Maintenance-Philosophy.md` (rules, TPM-based) and `docs/Plant-Facts.md` (the factories as they are) — read both before designing any maintenance module.
- **Standards and best practice**: Yantra must help the plant adopt industry maintenance standards and best practices (TPM, ISO 14224, EN 13306, ISO 55000, SMRP KPIs). At every design step, name the relevant standard or practice, explain in plain terms what it says and why, show how the proposal follows it — or state where and why it deliberately departs — and prefer standard terms over inventing local ones. The project owner is learning maintenance practice as the project goes.
- **RBAC deviation (S011)**: roles do not all come from the token. Keycloak gives only `maintenance_team` (may log in, grants nothing), `it_admin` and admin (`mspv-apps-admin`). The maintenance roles (`config_rbac.SITE_ROLES`) are held in Yantra per person and site (`memberships`, `person_units`; Team in Masters) and are read lazily per request. Keys in `config_rbac.SITE_SCOPED` are checked at the record's site (`has_perm_at`, `accessible_unit_ids(cur, key)`); others use the union. `config_rbac.py` stays the single source of roles and keys; fail-closed and the admin bypass are unchanged. New site-scoped keys must be added to `SITE_SCOPED`. Keycloak setup: `docs/Keycloak.md`.
- **Ports (dev)**: backend 5001, Vite 5176, MariaDB 3307 (3306 is SaralWeb's dev DB). Container backend listens on 5000.

- **Pre-flight (S049)**: run `/pre-flight` (or the **Pre-flight** run config, `tooling/common/preflight.py` with `TEST_CMD`) before asking the users for a maintenance window. On a green run it stamps the tested commit with a git note (`refs/notes/preflight`, never pushed; `git notes --ref=preflight show HEAD`); the release's step 2 then prints "Tests passed in pre-flight …" and skips `TEST_CMD`, when the stamp names HEAD's full sha, the same `TEST_CMD`, this computer, and is at most 7 days old (`preflight_stamp.STAMP_VALID_DAYS`). A stamp dated more than 5 minutes after now is not valid (`CLOCK_SKEW`). A red pre-flight removes any stamp on its commit (A2), so the newest result decides. Without a valid stamp the release tests as before, holding the pre-flight lock while `TEST_CMD` runs (A2: a pre-flight started then is refused instead of removing the release's test worktree; a lock error only warns); a release started while a pre-flight runs aborts before anything changes. The release commit (only `VERSION` changed) carries the stamp, so a retry after a failed build or deploy does not test again. `preflight_stamp.py gate "<test command>"` prints what the release would decide. The skill, `preflight.py`, `preflight_stamp.py` and `release.py` live in smtw-common (lifted 25-10-2026, `SMTW-WebApp-Base.md` § Pre-flight Before Every Release); Yantra keeps only its `## Pre-flight` settings and `tooling\release-tests.bat`.

- **Browser tests (S024)**: pattern and reasons: SMTW-WebApp-Base § Browser Testing Pattern. Playwright specs in `frontend/e2e/`, run by `tooling/run-e2e-tests.bat` (needs the dev DB container; creates `vel_yantra_e2e` and installs Chromium itself). Single stack (`E2E_LANES=1`): backend `127.0.0.1:5002` (`tooling/e2e/e2e_backend.py`, `vel_yantra_e2e` rebuilt every run, `DATA_DIR` `scratch/e2e-data/`, identity from `X-Test-Role` / `X-Test-User`), Vite 5177, seed `tooling/e2e/seed_e2e.py`; report `scratch/e2e-report/` (and `results.json`). Projects: `phone-chromium` (Pixel 7, the logic device), `desktop-chromium`, `phone-webkit` (iPhone 14). **WebKit in Docker (S046)**: when a run includes `phone-webkit`, `run_lanes.py` (inside the e2e lock) starts `mcr.microsoft.com/playwright:v<version>-noble` (the version of `frontend/node_modules/@playwright/test`) as container `yantra-e2e-webkit` on `127.0.0.1:3999` (`E2E_WEBKIT_WS`, `exposeNetwork: "<loopback>"` in `playwright.config.js`; log `scratch/e2e-lanes/webkit.log`; npm cache volume `yantra-e2e-npm`), removed after the run; a server that cannot start stops the run before any lane. `E2E_WEBKIT=native` runs WebKit on Windows (`e2e/support/test.js` skips it on a scaled display). **Levels (S047)**: `--level=basic|normal|full` (no flag is Normal). Basic: the `@smoke` tests (`journeys.spec.js`, four journeys, and `screens.spec.js`) on `phone-chromium`; refuses a `--grep`. Normal: every test on `phone-chromium`, the `@device` tests on `desktop-chromium` (`E2E_LEVEL=normal`, a project `grep` in `playwright.config.js`). Full: every test on `phone-chromium`, the `@device` tests on `desktop-chromium` and `phone-webkit` (`E2E_LEVEL=full`, S055). Checks a browser cannot judge are rows of `docs/steps/device-checks.md`.
- **Notifications (S021)**: Yantra is a PWA (`frontend/public/manifest.webmanifest`, `sw.js`). The service worker only shows a pushed alert and opens its ticket: it **caches nothing and has no `fetch` handler** (online-only; the stale-bundle check is unchanged) — never add caching to it. Alerts are enqueued in the ticket's transaction (`alerts.py`; rules in the pure `alerts_core.py`, the same for every channel) as `ticket_alert` / `ticket_escalate` tasks; the worker fans out one `push_send` per device (`push_subscriptions`, v24). A send task records its failure on its own row and commits before raising `NoRetry` / `RetryLater` (`task_handlers.py`). Push addresses are allowed only at the known push services (`push_core.ALLOWED_PUSH_HOSTS`, SSRF guard). VAPID keys are secrets in `secrets_app.py` (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`; empty = push off), made by `tooling/dev/make_vapid_keys.py`; production's pair is never rotated casually (it ends every subscription). `pywebpush` is called only in `push_sender.py`. **Email (S032)** is the second channel: each alert kind names its channels (`alerts_core.CHANNELS`; today only *Ticket closed* → email, to the site's managers); `smtplib` is called only in `mail_sender.py` (Mailgun, STARTTLS); secrets `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` (email is off unless host, port and from are set). **SMTP hosts, ports and email addresses never go into the repo**: CLAUDE-COMMON § Conventions, *Mail relay values and personal addresses*. A person's address is the Keycloak token's `email`, copied to `people.email` by `/api/auth/me`, shown only to IT admin and its owner; `email_send` payloads carry the person id.

- **Test command**: `tooling\release-tests.bat`
- **Tests a clean copy of HEAD**: `yes`
- **Failure logs**: the unit suites `scratch/release-tests/<suite>-tests-release.log` (suites `backend`, `frontend`, `tooling`), with one summary line each in `scratch/release-tests/test-summary-release.txt`; the browser tests `scratch/release-tests/e2e/results.json` (Playwright JSON) and the HTML report `scratch/release-tests/e2e/html/index.html`; the lane logs `scratch/release-tests/e2e/e2e-lanes/`.
- **Re-run failing tests**: backend `tooling/run-backend-tests.bat <file>::<test> …`; frontend `tooling/run-frontend-tests.bat <file> -t "<name>"`; browser `tooling/run-e2e-tests.bat --level=full e2e/<spec>:<line> … --project=<the failed project>` (one run per failed project). Set `YANTRA_TEST_RUN=preflight` for the backend re-run.
- **Known fault**: marked **strict**, with the fault and its step in the mark (KLA, S049 Q3): a browser test `test.fail(true, "S0NN: <the fault>")` as its first line; a backend test `@pytest.mark.xfail(strict=True, reason="S0NN: <the fault>")`; a frontend unit test `it.fails("…")` with a comment `// S0NN: <the fault>`. The rule: CLAUDE-COMMON § Engineering rules › *Known faults are marked strict*. (Yantra had no expected-to-fail mark before S049; `test.skip(condition, reason)` and the file-level `serviceWorkers: "block"` are not one.)
- **Release notes**: scratch/release-notes.md; readers: IT Admin, Admin and maintenance engineers of Yantra, a plant maintenance app

## Step workflow

Read by `/step` and its agents (S056). The skill, `.claude/agents/`, `tooling/steps/`, `tooling/roadmap/`, the `tooling/step-*.bat` wrappers, `tooling/render-mockups.bat` and the two READMEs come from smtw-common (lifted 26-10-2026, S057; CLAUDE-COMMON § Working in numbered steps) and are edited there, not here: a sync overwrites them. The step skill, `.claude/agents/`, `docs/steps/README.md` and `docs/roadmap/README.md` name no repo; Yantra's values are the entries below, and the generic text points at one as "(settings: *Entry*)". One bullet per entry, `- **Entry**: value`, as in `## Pre-flight`; an entry may be `none` (what that skips: `docs/steps/README.md` § The repo's settings and index).

Work is done in numbered steps (`S001`, …) whose brief, reviews and implementation report live in `docs/steps/` — read `docs/steps/README.md` for the file naming, finding IDs and gates before planning, reviewing or coding a step; the steps' index and queue are in `docs/steps/INDEX.md`. Never code a step whose brief is not `Approved` by the user. Big features are first cut into a roadmap (`docs/roadmap/`, its index `docs/roadmap/INDEX.md`, the `roadmapper` agent, `/step roadmap <feature>`, gate R; items `R0N.n` get a step number only when taken up). `/step` (skill) orchestrates the cycle from one terminal with the `brief-reviewer`, `coder` and `code-reviewer` subagents (`.claude/agents/`). `/step ls` builds its table from one run of `tooling/step-ls.bat`, and `/step check` (consistency of the step files, read-only) starts from `tooling/step-check.bat`, and `/step stats` (rounds, findings, time, tokens, e2e cost) from `tooling/step-stats.bat`, and `/step feedback` (the agents' `## Feedback` items: waste, hindrance, rule, idea) from `tooling/step-feedback.bat`; the orchestrator checks a draft brief's references with `tooling/step-brief-facts.bat S0NN` before review; at gate B each step is snapshotted as a commit under `refs/steps/S0NN` (`tooling/step-snapshot.bat snapshot|list|adopt`, step skill § Snapshots), so steps get their own commits while the next one is coded (`tooling/steps/`: `step_facts.py` reads the step files and git once; the scripts judge nothing the orchestrator should).

- **Unit tests**: all suites `tooling/run-tests.bat` (backend, frontend, tooling; it needs the dev DB up), once when the code is done, and in the code reviewer's rounds; while coding, only the tests of the modules changed: `tooling/run-backend-tests.bat <test files>` (pytest arguments pass through, e.g. `tooling/run-backend-tests.bat tests/test_tickets_core.py tests/test_ticket_work_api.py`), `tooling/run-frontend-tests.bat <file>` (vitest arguments pass through), `tooling/run-tooling-tests.bat`; build check `npx vite build` in `frontend/` when the frontend changed; test run name variable `YANTRA_TEST_RUN` (e.g. `YANTRA_TEST_RUN=s021cr3 tooling/run-tests.bat`; the orchestrator gives names such as `s021c1`, `s021cr2`), reserved names `dev` and `release` (the release's).
- **Browser tests**: Playwright specs in `frontend/e2e/`, run by `tooling/run-e2e-tests.bat` (`tooling/run-e2e-tests.bat --level=…` picks the level); the rules (levels, the `@device` tag, lanes, WebKit in Docker, the lock) are § Yantra Specifics, *Browser tests (S024)*. The S024 conventions: a test asserts what the user would see; a flow test calls `expectDialogFits` on every dialog it opens; allowed 400s, set-up by API, the open-dialog wait, per-lane databases. **Targeted run**: Normal with spec files: the specs of the screens and APIs the step changed (the spec-to-step map in § SMTW-Review) plus `e2e/screens.spec.js`, e.g. `tooling/run-e2e-tests.bat e2e/tickets-work.spec.js e2e/screens.spec.js`. **A new test alone**, on one lane and the logic device: `set E2E_LANES=1` then `tooling/run-e2e-tests.bat e2e/<spec>.spec.js --project=phone-chromium -g "S0NN"`. **Quick whole-app run**: Basic (`--level=basic`: the `@smoke` tests, the four journeys and `screens.spec.js`, on `phone-chromium`, about 2 minutes). **Whole-suite run**: Normal (`tooling/run-e2e-tests.bat`, no flag and no spec file: every test on `phone-chromium`, the `@device` tests on `desktop-chromium`). **Release level**: Full (`--level=full`: every test on the Android phone, the `@device` tests on desktop and the iPhone in its container); it runs only in the release (`tooling/release-tests.bat` runs it after the unit suites, on the same worktree of HEAD; § Yantra Specifics, *Release*) and when KLA asks. **Device projects**: `phone-chromium` (the Android phone, the logic device), `desktop-chromium` (desktop), `phone-webkit` (the iPhone); a `--project` you name runs every matching test there, e.g. `--project=desktop-chromium e2e/x.spec.js -g "S0NN"`. **Layout tag**: `@device` (`test("…", { tag: "@device" }, async …)`), only when the test's purpose is a layout check (its title names fits, in view, on screen, scrolls to, no sideways scroll, above or below; or its main assertion is a geometry), or it runs only on, or asserts differently on, a project other than `phone-chromium`. A logic test stays untagged, also when it calls `expectDialogFits` or `expectFieldMessage`: the Android phone checks those in every flow, and another device checks a dialog only through a `@device` test. **The lock**: one run at a time per machine, in the main working folder's `scratch/` (`scratch/e2e-run.lock`), so a worktree's run waits for it too (S047).

- **Code folders**: `backend` `frontend/src` `frontend/e2e` `frontend/tests` `tooling`; read by brief_facts.py: the folders git grep searches, and where a module and a test file are looked up; none = the whole repo except docs/.
- **Browser-test wrapper**: `run-e2e-tests.bat`; read by step_stats.py: the file name of the command that starts a browser run; none = no browser runs counted, no E2E columns.
- **Browser-test levels**: `basic` `normal` `targeted` `full`; the levels step_stats.py counts, in the order of its columns (header b/n/t/f); targeted is the reserved name of a run that names a spec file; two levels may not share a first letter.

## SMTW-Review

Read by `/smtw-review`: this repo's own points for the audit.

- **Browser tests**: the audit may run `tooling/run-e2e-tests.bat` (Playwright; `phone-webkit` needs Docker Desktop running and the WebKit image, S046, or `E2E_WEBKIT=native`) when it helps: to confirm a finding about a screen, a permission shown or hidden, or a flow (Normal with the spec file), or at `--level=full` to report the suite's state (every test on the Android phone, the `@device` tests on desktop and the iPhone). Run it in the background (a full run can pass the Bash tool's 10-minute limit; it needs the dev DB container up). Not required on every audit. Report the result, and every failing test with the screen it opens and the step it checks (the test names start with the step, e.g. `S017: …`; the spec files map to steps: `tickets-raise` S017/S018 A1, `tickets-work` S018/S052, `tickets-notes` S027, `notifications` S021, `me` S031/S064, `masters` S016/S037/S038/S043/S061/S063/S064, `equipment` S003/S006/S012/S038/S043/S039/S044/S061/S062/S063/S064, `readings` S039/S040/S050/S051/S064, `asset-list` S015/S062/S063/S064, `labels` S014/S064, `journeys` S047/S064, `screens` every route and S064, `changelog` S048, `floor` S064, `settings` S064). Tests marked as expected to fail or skipped carry a comment naming the open fault.
- **Steps**: check each committed step's status against its impl report (checks `[auto]`, ticked, skipped or pending) and list the steps that are committed but not `Done`.
- **Device checks**: list the open rows of `docs/steps/device-checks.md`.
- **Previous audit**: read the latest `docs/review/*-smtw-review.md` and report the status of each of its findings.
- **Migrations**: `_MIGRATIONS` starts at v20 (squashed 21-10-2026); v1–v13 live only in `backend/tests/fixtures/migrations_v13.py` and are never edited; a migration that touches rows that exist in production carries a `_PRECONDITIONS` entry and a test from the production schema. Check both on every migration after v20.
- **Meter readings (S039)**: every counter reading path (today `meters.log_reading`, which the S040 sheet also uses, row by row; later PM and IIoT feeds) takes the node lock first (`load_node_for_user`, `for_update`) and checks both neighbours (`meters_core.counter_error`, against the nearest active readings before and after the time taken). A path that skips the lock lets two writers pass the order check together; a path that checks only the latest reading lets a back-dated typo through.
- **How this section grows**: a step that adds something a later audit should check (a new invariant, a check that only a full run shows) adds a point here; the orchestrator proposes the point in the step's brief.
