## Findings

### BR2-01 — minor — The stamp's "working tree is clean" rule is redundant in the release and makes § 5 run 2 impossible on the coder's tree

**Problem.** § 1.3 *Valid* includes "the working tree is clean (`git status --porcelain` prints nothing)". In `release.py` this is already checked at line 90–94, before step 2, so the gate never sees a dirty tree there. Where it does matter is the `gate` CLI: § 5 run 2 expects `preflight_stamp.py gate "tooling\release-tests.bat"` to print "Tests passed in pre-flight …" "on a clean HEAD of the working folder". The coder's working folder is never clean while coding: the step's own files (`preflight.py`, `preflight_stamp.py`, the skill, the CLAUDE.md section) are untracked or modified, and the coder never commits. So run 2 prints "not valid: uncommitted changes", and run 1 (pre-flight with "Tests a clean copy of HEAD: yes") stamps HEAD while the tree is dirty, which the brief allows (decision 6). The two rules contradict each other: pre-flight may stamp with a dirty tree, but the stamp is then not "valid".

**Why it matters.** The coder either reports run 2 as failed, or works around it (a stash, a commit) that the rules forbid. And the stamp vouches for a sha; the state of the working folder is the release's concern, which `release.py` already refuses on its own.

**Options.**
- (a) **Recommended.** Drop the clean-tree rule from *Valid* (§ 1.3) and from `check`. `release_gate` stays a pure read of the note against HEAD, `TEST_CMD`, now and the machine. The `gate` CLI then prints the stamp's verdict alone, and run 2 works on a dirty tree. One line in § 1.3: "A dirty tree is the release's own refusal (`release.py:93`), not the stamp's."
- (b) Keep the rule, and let the `gate` CLI print two lines: the stamp's verdict and, separately, "The working tree has uncommitted changes; the release would refuse before the gate." Run 2's expected text changes to that.

### BR2-02 — minor — "The gate can only skip, never fail a release" needs an import guard and must cover step 4's carry

**Problem.** § 1.5 closes with "The gate can only skip tests, never fail a release: any error inside it is 'not valid', and the tests run." Two paths break that promise:
1. `import preflight_stamp` at the top of `release.py` (§ 3). After the lift, `sync_common.py` fetches `FILES` one by one and goes on after a failed fetch (`report_fetch_error`, lines 163–174): a repo can receive the new `release.py` and not `preflight_stamp.py` (a 404 while KLA is still adding it, a partial sync). Then every release in that repo dies on `ModuleNotFoundError` before step 0. Before the lift, the reverse sync (the old `release.py`) is harmless, as § 1.8 says.
2. Step 4's carry (`carry(release_sha)`) runs after the release commit and before the tag. The sentence covers "the gate"; the carry is not named. An exception there (git output, a note write) would abort a release whose tests passed and whose commit is made.

**Why it matters.** The whole value of the step rests on the release never being worse off than today. A crash at import is the worst form: no tests, no release, in the window.

**Options.**
- (a) **Recommended.** `try: import preflight_stamp` / `except ImportError: preflight_stamp = None`, and every call guarded by `if preflight_stamp`: the tests run as today, with one line "preflight_stamp.py not found; the tests run." Extend the sentence in § 1.5 to the carry and the write: all three (`release_gate`, `write`, `carry`) catch their own errors, print one warning line and return; a unit test for each that an exception inside gives "not valid" / `False` / no carry, never a raise. (The tests of `release_gate` with git stubbed already exist in § 3; add the raising stub.)
- (b) Keep the plain import and accept the crash as "the sync is broken, fix the sync". Simple, but the person finding it is KLA in a maintenance window of another repo.

### BR2-03 — minor — *Known fault*: `test.fail()` is not a Yantra convention today; choose the marker and state what it does

**Problem.** § 1.2 says "Yantra: `test.fail()` with a comment naming the open fault, CLAUDE.md § SMTW-Review". Checked: no spec in `frontend/e2e/` calls `test.fail` or `test.fixme`; the specs use `test.skip(<condition>, "<reason>")` (notifications.spec.js:88–153, screens.spec.js:108) and `testInfo.skip` in `support/test.js:19`. CLAUDE.md § SMTW-Review names no API; it says only "Tests marked as expected to fail or skipped carry a comment naming the open fault". The backend has no `xfail` either. The two markers behave differently, and the difference matters for this step's purpose:
- Playwright `test.fail()` is strict: the test runs, a failure counts as expected, and a **pass is reported as a failure** ("expected to fail but passed"). Good for a steady fault (the run turns red the day the fault is fixed, so the marker is removed), bad for a fault that passes now and then (a known fault that is also flaky keeps the run red at random).
- `test.fixme()` / `test.skip()` does not run the test; the run stays green whatever the code does, and nothing reminds anyone.
- pytest `xfail(reason=…)` tolerates a pass by default; `strict=True` behaves like Playwright's `test.fail()`.

**Why it matters.** The skill writes this setting's value into a fix-lane step's brief, and the coder of that step follows it. The brief presents a choice as an existing rule, and the choice decides whether a known fault can silently keep failing, or silently stay marked after it is fixed. This is the user's call.

**Options.**
- (a) **Recommended.** Playwright `test.fail("S0NN: <the fault>")` and pytest `pytest.mark.xfail(reason="S0NN: <the fault>", strict=True)` (checked; the marker's text is the comment the rule asks for); state in § 1.2 that both are strict, so the marker must come off when the fault is fixed, and that a fault that is also flaky goes to *Fix the test* instead. Write it as the new convention in CLAUDE.md's `## Pre-flight` section, not as an existing one.
- (b) `test.fixme` / `xfail` non-strict: never red, never a reminder. Simpler; the open fault then lives only in the step's brief and the queue.

### BR2-04 — minor — The pre-flight lock guards two pre-flights, not a Release started during one

**Problem.** § 1.4 step 2 answers BR1-09 with a lock on `scratch/preflight.lock` taken by `preflight.py`. `release.py` takes no lock, and `release-tests.bat` (its `TEST_CMD`) still removes `%TEMP%\yantra-release-tests` at its start (`:remove_worktree`: unlock, `remove --force`, `rmdir /s /q`). So **Release patch** clicked while `/pre-flight` runs in the background removes the live worktree under the pre-flight tests and makes a new one at the same path; the pre-flight's `:remove_worktree` later removes the release's. Traced: no path writes a green stamp without a green exit code, so no untested release follows; but both runs fail or run on each other's folders for 10 minutes, in the window.

**Why it matters.** The brief's own flow puts the two together: pre-flight in the background "any time before the window", the release in the window. One early click costs the window its tests. This is a judgement call (how much guard for one person's laptop), so it is not a nit.

**Options.**
- (a) **Recommended.** `release-tests.bat` (Yantra's own file, so no genericity cost) writes `%WT%\.running` with the start time after the worktree is made and deletes it at the end; at its start, a worktree with a marker younger than 30 minutes makes it refuse with exit 1: "Release tests are already running (started 14:02). Wait for them to finish." `release.py` then aborts with "Tests failed.", which is the safe side; an older marker is a cut-off run and is cleaned up as today. About eight lines of batch.
- (b) Accept it and say so: the skill's "started, about 12 minutes" line and one sentence in § 1.4 ("do not start a release while pre-flight runs") are the guard. Nothing to build; KLA holds the rule.
