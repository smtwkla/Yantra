## Findings

### BR1-01 — minor — § 5.6 step 2 and § 9 A2: the handler does not run in autocommit

**Problem.** The brief says the candidates read is "one plain read on its own (the worker's connection is autocommit)" and A2 says "each plan's `transaction(conn)` starts clean". Fact: `worker.Worker.run_one` wraps `run_task` in `with transaction(self.conn)`, so the handler starts inside a begun transaction, and the candidates read opens that transaction's REPEATABLE READ snapshot. The design still works, for a reason the brief does not give: the first per-plan `transaction(conn)` sends `BEGIN`, which implicitly commits the worker's open transaction (nothing was written in it), and after the handler's last `commit()` the connection is back in autocommit, so the worker's `mark_done` commits by itself and its outer `conn.commit()` is a no-op. The purge commits with `conn.commit()` per batch for the same reason.

**Why it matters.** The coder will write the brief's words into `pm_jobs.generate`'s docstring and `task_handlers.py`'s "third exception" text; a later reader who trusts them would reason wrongly about the snapshot (e.g. put a locking read before the loop).

**Options.** (a) Keep `transaction(conn)` per plan and state the mechanism (the implicit commit on `BEGIN`; `mark_done` autocommits after the last plan). (b) **Recommended:** add one explicit `conn.commit()` after the candidates read, as `purge_access_log` does, then `transaction(conn)` per plan; say in § 5.6 and A2 that the handler begins inside the worker's transaction and ends it there, so the loop relies on no implicit commit. Either way the RetryLater and RuntimeError paths are unchanged: the worker's rollback after the handler rolls back nothing committed.

### BR1-02 — minor — § 8.2: the serial tests assume a fresh counter

**Problem.** `serial_counters` is in conftest's `_TABLES`, emptied **once per session**, not per test. "A refused `POST` … the next job is still `…-001`" and "two jobs in one month number 1 and 2; the next month restarts at 1" hold only when no earlier test in the same worker database made a PM job in that month: the API tests (`test_pm_jobs_api.py`) and the run tests (`test_pm_generate.py`) both create jobs in the current month.

**Why it matters.** A test that passes or fails by test order is the kind the repo's *Known faults* rule forbids; it would turn red the first time the files run in another order or a test is added above.

**Options.** (a) **Recommended:** every test that asserts a serial fixes `pm_jobs._now` to a month of its own (the brief already monkeypatches it for the run; the save and the list read the same function, so the API tests can too), and the "no serial taken" test asserts the next serial is the one after the last job made in that month. (b) Assert relative numbers only (the second serial is the first plus one) and drop the "restarts at 1" case.

### BR1-03 — minor — § 8.4 runs: the seven-item bar is checked on the 390 px phone only at the release

**Problem.** The `phone-webkit` project (iPhone 14, 390 px) runs only at the Full level, i.e. in the release. S097 is the step that adds the seventh item; the Normal run checks the bar on the Pixel 7 (412 px) only. **Why it matters.** A red Full run at release time costs a maintenance-window slot; a 3-minute targeted run now costs nothing.

**Options.** (a) **Recommended:** add to § 8.4's runs, once, `tooling/run-e2e-tests.bat e2e/screens.spec.js --project=phone-webkit -g "S040"` (Docker Desktop running; the repo's tooling starts the WebKit container itself), with the result in the impl report. (b) Leave it to the release.

### BR1-04 — minor — § 5.7 and the `equipment.py` note: (6) after (6e) is a departure from the numbered order, and must be named as one

**Problem.** The LOCK ORDER numbers are the order locks are taken in: `improvements.py`'s *Not effective* takes "(6) the serial counter … before (6b) as the global order says" (its docstring, lines 80 and 147). S097 takes (6e) the plan, (1) the node, then (6) the `PM:` counter. The brief argues it correctly (only S097's creates take a `PM:` row, always under (6e); a REFRESH-only transaction must not bump the counter, so (6) cannot come first), but the text it writes into `equipment.py`'s note ("then, for a new job, (6) the PM:YYYY-MM counter") does not say it is a departure.

**Why it matters.** A later step (R03.4, or anything else that numbers a PM record) reads `equipment.py`'s note as the rule. Named as a departure with its reason, the rule stays "lower number first, except where a note says why"; unnamed, a reader either "fixes" S097 (burning serials) or copies (6e)-then-(6) for a counter that other modules also take, which is a real cycle.

**Options.** (a) **Recommended:** the `equipment.py` bullet and `pm_jobs.py`'s note both say: "(6) after (6e) and (1), a departure from the number order: the `PM:` counter row is taken by nothing else, and a plan transaction that only refreshes must not bump it." (b) Renumber the PM counter as its own level after (6e); more churn for the same fact.
